# 드래프트 룸 분석 노트 (v0.6 → v1.0.0)

v0.6 코드를 처음부터 끝까지 읽고 정리한 문서입니다. 1부는 게임이 어떻게 돌아가는지, 2부는 코드에서 발견한 문제와 이번에 고친 내용, 3부는 UI 개편 기준입니다.

---

## 1부. 게임 시스템

### 1.1 전체 구조

- **실행 형태**: `build.py`가 `src/`의 CSS 1개와 JS 22개를 `index.html` 한 파일에 인라인으로 넣습니다. 서버·설치·인터넷 없이 `file://`로 열어도 돌아갑니다.
- **모듈 방식**: 각 파일은 IIFE로 감싸 `window.DraftXxx` 전역에 등록합니다. Node 테스트에서는 같은 파일을 `require`로 읽습니다(UMD 비슷한 패턴). 로드 순서가 의존성 순서입니다.
- **결정성**: 모든 무작위는 문자열 시드 → FNV-1a 해시 → mulberry32 계열 PRNG(`prospects.js`의 `rng`)에서 나옵니다. 용도마다 시드 문자열이 다릅니다(`seed-pool-v6`, `seed-performance-v6-{연차}-{선수}-{팀}` 등). 그래서 **시드와 사용자의 선택만 알면 게임 전체를 똑같이 재현**할 수 있습니다. 저장 복원도 이 성질에 기대고 있습니다.
- **상태**: 게임 하나가 순수 JSON 객체(`createGame`의 `g`)입니다. 선수 풀은 저장하지 않고 필요할 때 시드로 다시 만듭니다(최근 3개 캐시).

```
core/                          ui/
 clubs ─ catalog ─ names ─ ko   format → setup / pregame / draft / postdraft / career / dialogs
 biography ─ grades             app (상태·이벤트·저장)
 prospects (풀 생성)
 scouting ─ season ─ draft-ai ─ press ─ career
 writer ─ voices (문장, 시뮬레이션과 분리된 난수)
 engine (진행·지명·저장 복원)  ← UI는 engine(DraftCore)만 봅니다
```

### 1.3 선수 생성 (`prospects.js`, `grades.js`, `biography.js`)

- **400명 구성**(0.7.0): 8개 지역 × 50칸. 각 지역 고졸 33명 + 나머지 17칸을 대졸 56 / 대학 얼리 24 / 2년제 24 / 국내 독립 12 / 해외 대학 6 / 마이너 복귀 10 / 해외 독립 복귀 3 / 특수 1칸으로 섞어 채웁니다. 특수 칸은 12% 확률로 MLB 경험자, 15% 확률로 NPB 2군·CPBL·LMB·ABL 복귀자가 됩니다. 20% 확률로 고졸 1명이 일본·미국 고교에서 뛴 야구 유학파로 바뀝니다.
- **2년제**: 4년제 얼리와 같은 나이(2학년)지만 현재 능력과 미래 능력의 차이가 조금 작습니다(6–11). 대졸 의무 지명 대상이며, 전용 리그와 '퓨처 베이스볼배 전문대학 야구대회'(4강 진출) 기록이 붙습니다.
- **구속**(0.7.0): 투수마다 어깨 힘을 한 번 뽑습니다. 어깨 힘은 구위를 조금 올리고 구속을 크게 올립니다. 그래서 구속은 빠르지만 제구·변화구가 낮아 순위가 밀리는 투수가 풀마다 20명 남짓 나옵니다. 공개 순위 1–10위 중앙값 151km/h, 61–110위 145km/h.
- **재능 구간**: 5단계 밴드에 110/56/24/8/2명을 섞어 배정합니다. 밴드가 기본 등급 범위(34–43 … 63–69)를 정합니다.
- **숨은 능력과 공개 능력**
  - `potentialTools`: 도달 가능한 상한(연속값).
  - `trueTools`: 현재 실제 기량. 상한에서 `gap`만큼 뺀 값이며, 고졸일수록 gap이 큽니다.
  - `tools`: 플레이어에게 보이는 값. 실제 기량에 **관측자 편향**(고졸 ±3.5, 그 외 ±2.5)과 잡음을 더해 5점 단위로 반올림합니다.
  - 공개 종합치: `ready`(현재), `scoutCeiling`(FV), `floorGrade`, `ceilingGrade`, 태그(즉전감/플로어/실링/육성형/역할형).
- **포지션별 가중치**: 선발은 구위 .30·커맨드 .25·변화구 .25·체력 .20, 포수는 수비 .48 등(`grades.js` `WEIGHTS`).
- **성장 곡선**: 조기 20% / 보통 58% / 늦은 22%. 고졸 밴드 2 이상 중 12%는 "원석(raw project)"으로 gap이 크고 성장률 편차가 큽니다.
- **아마추어 기록**: 현재 기량·학교 평판을 바탕으로 한 경기 수준 기록입니다. 해외 복귀자는 리그 레벨(A/AA/AAA/MLB)별 보정 기록으로 바꿉니다.
- **이력**: 출신 고교, 대학, 독립구단, 해외 소속까지 연도별 이력을 만듭니다. 지역 1차 자격은 **현재 고교 졸업예정자이면서 그 고교의 지역**으로만 판정합니다.

### 1.4 드래프트 (`engine.js`, `draft-ai.js`, `scouting.js`)

- **지명 가능 목록** `available()`
  - 지역 1차: 해당 연고 지역 고졸 자격자만.
  - 대졸 의무: 아직 대졸을 못 뽑은 구단이 남은 지명권 수 ≤ 부족 인원이면 대졸만 보입니다. 반대로 대졸을 이미 채운 구단은 남은 대졸 수 ≤ 전체 부족 수일 때 대졸을 못 뽑습니다(다른 구단 몫 보호).
- **CPU 지명** `aiScores()`: 공개 정보만 봅니다(`project()`가 숨은 필드를 걸러 냄).
  - 이지: 공개 점수 + 적합도 약간 − 같은 포지션 수, 잡음 ±6.
  - 노말: 팀장 성향 점수 − 포지션 중복 ×2, 잡음 ±2.5.
  - 하드: 중복 ×3.5, 보강 포지션 희소성 가산, 잡음 ±0.75.
- **팀장 성향**: 균형/즉전/안정/실링 중 하나와 출신 선호, 보강 포지션별 세부 수요(예: "커맨드 45+ 불펜")를 게임마다 뽑습니다. 적합도 = 보강 1·2·3순위 100·80·60 × 세부 툴 달성도(최소 74%). 보강 포지션이 아니면 25입니다.

### 1.4½ 계약 (`contracts.js`, 0.9.0)

- **예산**: 1350 ± 150(백만 원) + 지역 1차 300. 계약금과 육성선수(1명 30)가 모두 여기서 나갑니다.
- **요구액**: `max(순번 관례액, 0.4 × 순번 관례액 + 0.6 × 공개 순위 관례액) × 의향 배수(진학 1.35, 해외 2.2) × 응원 팀 0.85`. 관례액은 1라운드 4.5억 → 2.25억, 2라운드 1.5억, 3라운드 1.1억, 4라운드부터 8500만 → 3500만, 지역 1차 3억.
- **첫 제시 수락**: 기본(의향 없음 82%, 진학 50%, 해외 20%) + (제시/요구 − 1) × 2.5 + 응원 팀 15% + 난이도(쉬움 +5%, 어려움 −5%), 요구액의 70% 미만이면 −30%, 최대 98%. 수락하지 않으면 재요구(의향 없음 100%, 진학 65%, 해외 35%, 요구액의 1.1배) 또는 거부.
- **CPU**: 뒤 순번 관례액의 85%와 육성선수 3명분을 남기고 요구액까지 제시합니다. 재요구는 예산이 되면 받아들입니다.
- **의향**: 고졸 FV 50+ 중 12%가 진학 희망, 공개 순위 15위 안의 FV 60+ 고졸 중 25%(풀당 최대 2명)가 해외 구단 관심. CPU는 난이도별로 이런 선수의 점수를 깎습니다(보통 −2/−6, 어려움 −3/−9).
- **남은 예산**: `남은 비율 × 0.5`(최대 15%)만큼 그 구단 선수의 성장 속도를 첫 3시즌 동안 높입니다.
- 600회 실험에서 리그 전체 지명 거부는 드래프트당 약 2명, 남는 예산 중앙값은 12%입니다.

### 1.5 언론·팬·약속 (`press.js`)

- 모의 지명 2종: 현재 기량 비중 68%(다이아몬드 데일리)와 25%(퓨처 베이스볼).
- 지역 1차·1라운드 지명마다 기사와 댓글 3개가 생기고, 팬심이 −5…+5 움직입니다(예측 적중, 보강 적합, 이른 지명, 포지션 중복).
- 단장 약속 3종(1군 경험 2명 / 60%가 계획 이행 70점 / 보강 3개+이행 2명)은 첫 시즌 뒤 −4…+4점으로 첫해 평가에 반영됩니다.

### 1.6 시즌 시뮬레이션 (`season.js`, `tuning.js`)

선수 한 명의 한 해는 다음 순서로 정해집니다. 단계마다 `season.js`의 함수가 하나씩 있습니다(`rollHealth` → `decideRole` → `firstTeamGames` → `hitterStats`/`pitcherStats` → `developTools` → `planScoreOf`). 아래 숫자는 모두 `tuning.js`에 모여 있습니다.

1. **건강**: `risk`(5–16%) 확률로 부상. 22%는 장기(65–130일)이고, 105일 이상이면 재활로 시즌을 접습니다.
2. **보직**
   - 작년에 주전이었으면 85% 안팎으로 유지합니다(기량·작년 성적 보정).
   - 아니면 기량 시그모이드 + 상위 지명 투자(1R 첫해 +18%) + 적합도로 콜업 여부를 정하고, 다시 주전/백업/짧은 경험을 나눕니다.
   - 0.8.0부터 콜업 기준(기량 46.5)과 주전 기준(52.5 → 2년 차부터 51)을 1군 기존 선수 수준에 맞췄습니다. 이전에는 기준이 낮아 10년이면 11라운드 지명자의 98%가 1군에 데뷔했습니다.
   - 동기 중 같은 팀·포지션 정원(선발 2, 불펜 3, 포수 1, 내야 2, 외야 2)을 넘으면 백업으로 내립니다. 한 드래프트가 1군 로스터를 채우지 못하게 하는 장치입니다.
3. **출전량**: 연차가 늘수록 늘어납니다(야수 주전 88 → 105 → 120경기 + 무작위).
4. **기록**: 야수는 타석 단위 시뮬레이션(볼넷 → 홈런 → 안타 → 삼진 확률이 툴에 연동), 투수는 등판 단위(포아송 실점·삼진·볼넷, 선발승은 5이닝 이상 + 실점 + 팀 순위).
5. **성장**: 툴마다 `(상한 − 현재) × 곡선별 비율 × 나이 감쇠 × 개인 성장률`에 잡음을 더하고, 부상과 노화(주력 26세, 나머지 29세부터)를 뺍니다. 나이 감쇠는 22세까지 1이고 28세에 거의 0이 됩니다(늦게 크는 선수는 2년 늦게). 그래서 나이 많은 지명자는 상한까지 다 크지 못합니다. 성장 후 다시 관측해 공개 등급을 갱신합니다. 프로 연차가 쌓일수록 관측 오차가 줄어듭니다.
6. **점수**: 계획 이행(성장 달성도 중심), 1군 기여 지수(이닝·ERA 또는 타석·OPS·수비), WAR 추정치.
   - 야수 WAR: 선형 가중치 wOBA로 만든 타격 득점 + 포지션 보정(포수 +10, 내야 +2.5, 외야 −4) + 수비 툴 + 도루 + 대체 수준(600타석당 20점), 10점 = 1승.
   - 투수 WAR: 역할별 대체 투수 실점률 대비 실점(ERA × 1.08)으로 계산합니다. 피안타를 시뮬레이션하지 않아 FIP·WHIP는 없습니다.
7. **FV 재평가**: 매 시즌 스카우트가 `지금 기량 + 나이로 남은 성장 여지 × (상한 − 기량)`을 새로 추정하고, 작년 FV와 6:4로 섞습니다.

### 1.6½ 육성 계획·포지션·이도류 (`career.js` planStep, 1.0.0)

- **반대쪽 재능**: 모든 선수에게 반대쪽(투수의 타격, 타자의 투구) 능력이 숨어 있습니다. 풀 생성 뒤 별도 난수로 만들어 기존 재능은 바뀌지 않습니다. 대부분 낮고(잠재 22–40 + 본래 잠재의 40%), FV 45 이상이면 스카우트 메모로 공개됩니다.
- **이도류 유망주**: 풀당 35% 확률로 1명, 10% 확률로 1명 더(공개 순위 40위 안, 해외 경력 없음). 반대쪽 잠재가 본래 잠재보다 0–4 낮습니다.
- **선수 상태**: 현재 포지션(`role`), 현재 쪽 툴·잠재, 반대쪽(`other`) 툴·잠재·공개 평가를 따로 가집니다. 시즌 시뮬레이션에는 현재 포지션 기준의 선수 모습(`viewOf`)을 넘깁니다.
- **포지션 변경**: 선발→불펜 구위 +2, 불펜→선발 −1. 포수→내야 수비 −3, 포수→외야 +2, 내야→외야 +3, 외야→내야 −5. 투수↔타자 전향은 반대쪽 툴과 자리를 맞바꿉니다. 첫 시즌은 콜업 판단 −2, 성장 0.8배입니다.
- **CPU 습관**(2년 차부터): 공개 체력 40 미만 선발 → 불펜 25%, 공개 수비 38 미만 포수 → 내야 20%, 만 24세 이하에서 반대쪽 공개 평가가 5 이상 높으면 전향 50%, 이도류는 3년 차부터 두 쪽 차이 10 이상이면 접습니다. 600회 실험에서 드래프트당 선발→불펜 약 6명, 포수 이동 약 3명, 투타 전향 0.05명.
- **이도류 시즌**: 두 쪽을 각각 시뮬레이션합니다. 부상은 한 번 굴려 두 쪽에 같이 적용하고, 두 번째 포지션은 주전 불가·출전 0.55배입니다. 성장은 두 쪽 모두 0.75배이고, WAR은 합칩니다.
- **육성 방향**: 고른 툴은 성장 1.6배, 나머지 0.85배. 상무 복무 중에도 적용됩니다.
- 사용자 계획은 저장에 `plans: [[시즌, 선수, 방향, 포지션, 겸업]]`으로 남고, 아무것도 바꾸지 않는 계획이 들어간 저장은 거부합니다.

### 1.7 10년 경력 (`career.js`)

### 1.8 저장

- 자동 저장: `localStorage['draft-room-kbo-v6-scouting']`. 파일 저장도 같은 내용의 JSON입니다.
- 저장 형식(v0.6.2부터): **게임의 입력만** 담습니다. 10시즌 진행이 약 450바이트입니다(v0.6.0은 약 560KB, 내보낸 파일은 1.3MB).
  ```json
  {"format":"draft-room-save","version":2,"sim":"0.8","teamId":"lg","local":true,"seed":"…",
   "difficulty":"normal","rounds":11,"phase":"owner","picks":["p015","p042",…],"dev":["p301"],
   "gmChoice":"development","seasons":10,"service":[[2,"p260","sangmu"]]}
  ```
  `picks`는 사용자 구단의 지명만 담습니다. CPU 지명, 기사, 시즌 기록은 불러올 때 다시 계산합니다(10시즌 기준 약 0.2초).
- **`sim`(시뮬레이션 버전)**: 결과를 다시 계산하는 방식이라, 시뮬레이션이 바뀌면 같은 입력이 다른 역사가 됩니다. 그래서 저장에 `SIM_VERSION`(`src/core/engine.js`)을 기록합니다.
  - 버전이 다른 저장은 **거부합니다**. 조용히 다른 결과로 다시 만들지 않습니다.
  - 자동 저장이면 `…-sim-<버전>` 키로 따로 보관하고 안내 문구를 띄웁니다.
- **버전 올리기 강제**: `tests/golden.cjs`가 시뮬레이션 결과(숫자·지명) 해시를 `SIM_VERSION`과 함께 기록합니다.
  - 결과가 바뀌었는데 버전이 그대로면 테스트가 실패하고, 기준을 다시 기록하는 것(`--write`)도 거부합니다.
  - 밸런스를 고칠 때는 버전을 올리고 기준을 다시 기록하면 됩니다.
- v0.6.0 형식(게임 객체 전체)은 0.6.x까지 불러올 수 있었습니다. 0.7.0은 `sim` 0.7이므로 0.6 저장은 모두 거부하고, 자동 저장은 `…-sim-0.6` 키로 보관합니다. 0.7 저장에는 `rounds`와 육성선수 계약 `dev`가 추가됐습니다.

### 2.2 코드 가독성

- **한 줄에 수천 자**: `catalog.js` 한 줄 20,364자, `view05.js` 4,446자, `app.js` 2,700자 등. 사실상 압축된 코드여서 diff·리뷰가 불가능했습니다.
  - 코어 로직은 포매터로 펼친 뒤 손으로 정리했습니다. 매직 테이블은 이름 붙은 상수로 뺐습니다(`TALENT_BANDS`, `PITCHER_SHAPES`, `OTHER_PATHWAYS` 등).
  - 데이터 파일(`catalog`, `clubs`)은 한 줄에 레코드 하나씩 두었습니다.
- **버전 번호가 붙은 파일명**: `view04/05/06.js`, `rules04.js`, `grades06.js`, `scouting06.js`. 이름으로는 역할을 알 수 없었습니다. 역할 이름으로 바꿨습니다(`draft-ai.js`, `grades.js`, `scouting.js`, `ui/draft.js` …).

- **엔진에 대사가 섞임**: `engine.js`의 절반이 인터뷰·감독 코멘트·스카우트 조언 문장이었습니다. `core/voices.js`로 분리하고, 엔진이 설치하는 방식으로 순환 의존을 피했습니다.

### 2.3 저장 복원 설계

- **이전 방식**: 저장 파일의 모든 파생 데이터(기사 문장, 추천 문장, 시즌 기록…)를 재생 결과와 **문자열까지 똑같이** 비교했습니다. 그래서 오타 하나만 고쳐도 모든 플레이어의 저장이 조용히 무효가 되는 구조였습니다. 게다가 CPU 구단의 지명은 AI 선택과 비교하지 않아서, 규칙에만 맞으면 다른 선수로 바꿔도 통과했습니다.
- **새 방식 `restore()`**: 저장에서 시드·구단·설정·지명·기자회견 답·진행 시즌 수만 읽고 게임을 처음부터 다시 계산합니다.
  - CPU 지명은 AI가 실제로 할 선택과 같아야 합니다.
  - 파생 데이터를 고쳐도 무시되고 정직한 값으로 복구됩니다.
  - 문구를 고쳐도 기존 저장이 그대로 열립니다(v0.6.0 데모 저장의 모든 숫자·지명이 똑같이 복원됨을 확인).
  - v0.6.2에서 한 단계 더 나아가 저장 자체를 입력만 담는 형식으로 바꿨습니다(1.8 참고).

  - 팬 댓글: 커뮤니티 말투(욕설 없음)
